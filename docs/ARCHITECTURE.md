# Architecture

Vortex-Ai-Chat is a Cargo workspace of six crates. Everything is Rust; the
browser UI compiles to WebAssembly (Leptos 0.8 CSR) and talks to the server
over REST + SSE. There is no JavaScript application code — only the
wasm-bindgen glue generated by the Rust toolchain.

```
crates/
  vortex-types     Shared serde DTOs: chat messages, run events, settings,
                   capabilities. Dependency-light so it compiles to WASM too.
  vortex-core      XDG paths, boot config (.env + config.toml), SQLite
                   (rusqlite, bundled, WAL) behind spawn_blocking, migrations,
                   stores for conversations/messages/settings/runs/tool calls/
                   approvals/checkpoints.
  vortex-llm       Provider abstraction + OpenRouter streaming client
                   (SSE parse, tool-call accumulation, bounded retries) and
                   mock provider. Trait: complete(request, event-sink).
  vortex-agents    The engine: tool registry & validation, workspace
                   confinement, SSRF-safe HTTP, search providers, file/command/
                   preview/browser tools, approvals, event hub, scheduler
                   (global sub-agent cap), and the run loop.
  vortex-server    Axum binary: REST + SSE, static embedded UI, request guards,
                   graceful shutdown with process cleanup.
  vortex-ui        Leptos CSR UI -> wasm32-unknown-unknown (Trunk build).
```

## Data flow (one chat message)

```
UI (WASM) --POST /api/conversations/{id}/chat--> server
  server: persist user message, start run ------------> Engine::execute_run
    loop:
      LlmClient::complete(messages, tool_schemas)      --> OpenRouter SSE
        text deltas -------------------------------------> hub broadcast --> SSE --> UI
        tool_calls? -> registry.execute (validate, permissions, approvals)
                       tools may spawn sub-agents (scheduler-gated)
      until final answer -> persist message --> RunFinished event
```

## Key components

### Agent loop (`vortex-agents/src/engine.rs`)
Each run iterates: model call (streaming deltas forwarded to subscribers) ->
tool calls (executed concurrently, validated and permission-checked) -> tool
results appended as `tool` messages. Budgets: max iterations, wall-clock
deadline, token budget. Cancellation is a `CancellationToken` tree — cancelling
a coordinator cancels all descendants.

### Scheduler (`vortex-agents/src/scheduler.rs`)
A dynamic counter+Notify gate: `acquire()` returns a `SlotGuard` whose `Drop`
releases the slot (cancellation-safe). Limit default 6, ceiling 16, changeable
at runtime. The coordinator never takes a slot; nested sub-agents acquire from
the same global gate.

### Tool registry (`vortex-agents/src/registry.rs`)
Single enforcement point: enabled-set check (the run's allow-list), typed
parameter validation (specs generate the JSON Schema given to the model),
risk classification, and execution. `Risk::Consequential` always routes through
the approval gate regardless of profile — including for sub-agents.

### Workspace confinement (`vortex-agents/src/workspace.rs`)
Root is canonicalized at selection. Model paths are resolved relative to it;
absolute paths must already be inside; `..` is rejected outright; every
existing component is canonicalized so symlink escapes fail. File writes
serialize on a per-path async mutex, enforce cross-run ownership (a sub-agent
cannot overwrite another agent's file; the coordinator reconciles), snapshot
the previous content as a checkpoint, and produce a unified diff.

### Approvals (`vortex-agents/src/approvals.rs`)
`ApprovalGate::request` persists the request, streams `ApprovalRequested`, and
awaits a oneshot that only the server API (`POST /api/approvals/{id}/decide`)
can resolve. Timeout auto-denies. Models have no path to approval.

### Previews (`vortex-agents/src/preview.rs`, `preview_server.rs`)
Static previews are served by a small loopback-only Rust HTTP server
(GET/HEAD only, path confinement, ephemeral port). Dev-server previews spawn
the project's own tooling in a dedicated process group; the port is parsed
from its stdout. Every preview is owned by its run and killed (SIGTERM ->
SIGKILL on the whole group) when the run ends, is cancelled, or the server
shuts down.

### Browser (`vortex-agents/src/browser.rs`, `cdp.rs`)
A Chromium/Chrome binary is detected in PATH (`VORTEX_CHROME_PATH` overrides).
It is launched headless with its own `--user-data-dir` under the XDG cache and
its own process group, and spoken to via a minimal Chromium DevTools Protocol
client over a loopback websocket (Target.createTarget/attachToTarget,
Page.navigate, Runtime.evaluate). Pages are per-run and closed when the run
ends; the browser group is killed at shutdown. Missing binary => tools report
unavailable with setup instructions.

### Server (`vortex-server`)
Request guard middleware enforces Host-header allow-listing (DNS-rebinding
defense), Origin checks on writes, and — in opt-in LAN mode — bearer-token
auth. SSE streams fan out per run via tokio broadcast (child events are also
published on ancestor channels, so one subscription covers the agent tree).
`rust-embed` bakes `ui-dist/` into the release binary.

## Persistence schema (SQLite)

`conversations`, `messages`, `settings`, `runs` (status/usage/plan),
`tool_calls`, `approvals`, `checkpoints`. On startup, runs still marked
queued/running/waiting-approval are set to `interrupted` — nothing is replayed
automatically.

## Build pipeline

`scripts/build-release.sh` = Trunk (Leptos -> wasm-bindgen -> wasm32) into
`crates/vortex-server/ui-dist/`, then `cargo build --release -p vortex-server`
(embeds `ui-dist/`). Debug builds read `ui-dist/` from disk so UI changes are
picked up without rebuilding the server.
