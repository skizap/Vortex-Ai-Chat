# Developer guide

Vortex-Ai-Chat — a local-first, Linux-only AI assistant written entirely in
Rust. This guide covers setup, running the app locally, architecture,
component internals, the HTTP API, the data model, agent-loop semantics, and
testing.

> **A real OpenRouter API key is required for the application to function.**
> The built-in mock provider is an offline test harness for the
> request/tool/SSE plumbing only — it does not provide assistant
> functionality and is not a substitute for a key (see
> [§5](#5-mock-provider-test-harness-only)).

Companion docs: [`ARCHITECTURE.md`](ARCHITECTURE.md) (overview),
[`SECURITY.md`](SECURITY.md) (threat model),
[`KNOWN_ISSUES.md`](KNOWN_ISSUES.md) (findings with file:line evidence),
[`../AGENTS.md`](../AGENTS.md) (AI-agent orientation).

## 1. Overview & architecture

Six crates in a Cargo workspace; dependency direction is strictly downward:

```
vortex-server   Axum binary: REST + SSE, request guards, embedded UI assets
vortex-ui       Leptos CSR UI → wasm32-unknown-unknown (Trunk build)
     │
     ▼
vortex-agents   Engine: run loop, tool registry, workspace confinement,
     │          approvals, scheduler, previews, browser/CDP, search, hub
     ▼
vortex-llm      LlmClient trait, OpenRouter streaming client, scripted mock
     │
     ▼
vortex-core     Paths, boot config, SQLite store (WAL, spawn_blocking)
     │
     ▼
vortex-types    Shared serde DTOs (chat, events, settings) — also compiled
                into the WASM UI so both sides share one typed contract
```

There is no JavaScript application code — only wasm-bindgen glue generated by
the Rust toolchain. The UI talks to the server exclusively over relative
`/api` paths (`crates/vortex-ui/src/api.rs:9`), so **the UI must be served by
the Axum server**; there is no standalone `trunk serve` frontend workflow.

One chat message end-to-end:

```
UI (WASM) ──POST /api/conversations/{id}/chat──▶ server (routes_conv.rs)
  persist user message (SQLite) ──▶ Engine::start_chat_run
    register run in Hub (broadcast chan) + DB ──▶ spawn detached task
    run_loop:
      LlmClient::complete(request, event-sink)   ──▶ OpenRouter SSE
        TextDelta ──▶ Hub broadcast ──▶ SSE /api/runs/{id}/events ──▶ UI
        tool_calls? ──▶ ToolRegistry::execute
                          (allow-list → schema validation → risk class →
                           approval gate if Consequential → tool)
                          tools may spawn sub-agents (scheduler-gated)
      append tool results as `tool` messages; repeat until final answer
    persist assistant message ──▶ RunFinished event ──▶ UI refetches messages
```

## 2. Requirements

Tested baseline: Linux Mint 22.3 / Ubuntu 24.04, x86_64. Linux only.

| Requirement | Why | Install |
| --- | --- | --- |
| Rust **1.89.0** | pinned by `rust-toolchain.toml`; rustup enforces it | `rustup` picks it up automatically |
| cc toolchain, `pkg-config` | bundled SQLite (rusqlite `bundled`) needs cc | `sudo apt install build-essential pkg-config` |
| `libsqlite3-dev` | SQLite headers | `sudo apt install libsqlite3-dev` |
| **OpenRouter API key** | **required — the assistant cannot function without one** | <https://openrouter.ai/keys> → put in `.env` |
| Trunk | UI (WASM) builds only | `cargo install trunk --version 0.21.14 --locked` (0.22+ needs rustc ≥ 1.96) |
| wasm-bindgen-cli **0.2.129** | UI builds only; must equal the `wasm-bindgen` version in `Cargo.lock` or Trunk fails | `cargo install wasm-bindgen-cli --version 0.2.129` |
| Chromium (optional) | browser tools | `sudo apt install chromium`, or set `VORTEX_CHROME_PATH` |
| SearXNG (optional) | research-mode web search | e.g. `docker run --rm -p 127.0.0.1:8888:8080 searxng/searxng` with JSON output enabled |

No Python, no Node.js.

## 3. Running the website locally (dev)

From a fresh clone:

```bash
git clone https://github.com/skizap/Vortex-Ai-Chat.git
cd Vortex-Ai-Chat
cp .env.example .env          # edit: set OPENROUTER_API_KEY to your real key
chmod 600 .env                # keep secrets private
scripts/build-ui.sh           # Trunk → crates/vortex-server/ui-dist (required!)
cargo run -p vortex-server    # debug server on http://127.0.0.1:8417
```

Open <http://127.0.0.1:8417>.

Important behaviors:

- **`ui-dist/` is gitignored.** A fresh clone has no UI assets; the server
  still compiles (`crates/vortex-server/build.rs` writes a placeholder
  `index.html`) and serves an instructional placeholder page until you run
  `scripts/build-ui.sh`.
- **Debug builds read `ui-dist/` from disk** (rust-embed debug mode), so the
  UI iteration loop is: `scripts/build-ui.sh` → refresh the browser. No
  server recompile needed.
- **Release builds embed `ui-dist/` at compile time** — after a UI change you
  must also rebuild the server (`cargo build --release -p vortex-server`).
- First run creates `~/.config/vortex/`, `~/.local/share/vortex/` (SQLite DB
  at `data/vortex.db`, WAL mode), and `~/.cache/vortex/`.
- In the UI: set a **workspace root** (sidebar) before using coding/file
  tools — file tools are refused until one is set. Set the model in
  Settings (the catalog is fetched from OpenRouter via `GET /api/models`).

## 4. Release build & run

```bash
scripts/build-release.sh          # build-ui.sh + cargo build --release -p vortex-server
./target/release/vortex-server    # single self-contained binary, UI embedded
# open http://127.0.0.1:8417
```

Release profile: thin LTO, 1 codegen unit, stripped (`Cargo.toml:62-65`).

## 5. Mock provider (test harness only)

```bash
VORTEX_LLM=mock ./target/release/vortex-server
```

This starts the server against a built-in scripted provider — **no network,
no key**. It exists to exercise the request/tool/SSE plumbing offline (development
and tests):

- `VORTEX_MOCK_SCRIPT=echo` (default) — streams "You said: <message>".
- `VORTEX_MOCK_SCRIPT=tools` — performs one `web_search` tool round-trip
  against the mock search provider and streams an answer quoting the tool
  evidence, proving the full tool pipeline (tool call → registry validation →
  execution → result → streamed answer).

**The mock is not a way to use the assistant.** It produces canned text, has
no model behind it, and does not provide real chat, research, or coding
functionality. Real use requires a real OpenRouter API key. With `tools`
scripting, every run performs the tool round-trip (the turn is derived from
the request, not a process-global counter — `docs/KNOWN_ISSUES.md` C8,
fixed).

Without a key and without the mock, the server still starts (so the UI can
show setup guidance), but `POST /api/conversations/{id}/chat` returns
`503` with configuration instructions (`routes_conv.rs:126-132`).

## 6. Configuration

Three layers, resolved at startup in `AppConfig::load`
(`crates/vortex-core/src/config.rs:89-140`).

**Precedence (highest wins):** process environment → `.env` file (working
directory) → `~/.config/vortex/config.toml` → built-in defaults. (`.env`
never overwrites variables already present in the environment,
`config.rs:181`.) The API key is resolved lazily: env var named by
`llm.api_key_env` (default `OPENROUTER_API_KEY`) first, then
`llm.openrouter_api_key` from config.toml (`config.rs:147-158`).

### config.toml (boot-level; all keys optional)

```toml
[server]
host = "127.0.0.1"   # loopback enforced; non-loopback refuses to start
port = 8417          # unless [server.lan] enabled = true

[server.lan]         # OFF by default; opt-in LAN exposure, token-gated
enabled = false
token = ""           # auto-generated (32 bytes hex) on first LAN boot,
                     # persisted to config.toml with 0600 perms

[llm]
provider = "openrouter"                    # or "mock"
base_url = "https://openrouter.ai/api/v1"
# openrouter_api_key = "sk-or-..."         # prefer the env var / .env
api_key_env = "OPENROUTER_API_KEY"
mock_script = "echo"
```

`log_level` defaults to `"info"` (`RUST_LOG` overrides).

### Environment overrides

| Variable | Effect |
| --- | --- |
| `OPENROUTER_API_KEY` | API key (or the name set by `api_key_env`) |
| `VORTEX_HOST` / `VORTEX_PORT` | bind address/port (loopback rule still enforced) |
| `VORTEX_OPENROUTER_BASE_URL` | OpenRouter-compatible endpoint |
| `VORTEX_LLM` | `openrouter` (default) or `mock`; other values ignored |
| `VORTEX_MOCK_SCRIPT` | `echo` / `tools` (mock mode only) |
| `VORTEX_CHROME_PATH` | explicit Chromium/Chrome binary for browser tools |
| `VORTEX_CONFIG_DIR` / `VORTEX_DATA_DIR` / `VORTEX_CACHE_DIR` | storage overrides (must be absolute) |
| `RUST_LOG` | tracing filter |

Note: the search provider (SearXNG) URL is runtime state stored in SQLite —
configure it in Settings → Search. There is no environment override for it
(the formerly advertised `VORTEX_SEARXNG_URL` was never read and has been
removed from `.env.example`).

### Storage locations

| Purpose | Default | Override |
| --- | --- | --- |
| Config (`config.toml`) | `$XDG_CONFIG_HOME/vortex/` (fallback `~/.config/vortex/`) | `VORTEX_CONFIG_DIR` |
| Data (SQLite DB, trash) | `$XDG_DATA_HOME/vortex/` (fallback `~/.local/share/vortex/`) | `VORTEX_DATA_DIR` |
| Cache (browser profile) | `$XDG_CACHE_HOME/vortex/` (fallback `~/.cache/vortex/`) | `VORTEX_CACHE_DIR` |

Precedence: `VORTEX_*_DIR` (must be absolute) > absolute `XDG_*_HOME` >
`$HOME` defaults. Relative `XDG_*_HOME` values are ignored per the XDG spec.

### Runtime settings (SQLite, editable in the UI Settings tab)

Model, temperature (0.0–2.0), max tokens (64–100 000), theme, default mode,
workspace root, command allowlist, search provider URL, per-tool toggles
(files/search/browser/commands/previews/delegation), permission profile
(`restricted`/`standard`/`trusted`), and agent limits (concurrency 1–16,
max iterations 1–64, run timeout 30–3600 s, approval timeout 10–3600 s,
token budget, recursive delegation). Values are clamped server-side on
`PUT /api/settings` (`routes_misc.rs:20-62`). Defaults:
`vortex-types/src/settings.rs:102-153` (model `openrouter/auto`, temperature
0.7, max_tokens 4096, 6 concurrent sub-agents, 16 iterations, 600 s run
timeout, 200 000 token budget, 300 s approval timeout, commands **off**,
recursive delegation **off**).

## 7. Component walkthroughs

### vortex-types (`crates/vortex-types/src/`)

Shared serde contract compiled into both server and WASM UI.
`chat.rs`: `Role`, `ChatMessage` (OpenAI-shaped, with `tool_calls` /
`tool_call_id`), `ToolCall { id, name, arguments(raw JSON string) }`,
`Usage`, `ModelInfo`. `events.rs`: `RunStatus` (queued/running/
waiting_approval/completed/failed/cancelled/interrupted), `RunEvent` (tagged
enum — the SSE event catalog, see §9), `PlanStep`. `settings.rs`: `Settings`
and sub-structs (§6), `PermissionProfile`, `AgentSettings::MAX_LIMIT_CEILING
= 16`. `dto.rs`: REST payloads (`ConversationSummary`, `StoredMessage`,
`RunInfo`, `ToolCallRecord`, `ApprovalInfo`, `PreviewInfo`, `Capabilities`).
`lib.rs`: `Mode` (chat/research/coding/browser/agent). `jobs.rs`: the durable
autonomous-work contract — `Routine`/`RoutineVersion`/`RoutineStatus`,
`Job`/`JobStatus` (draft/active/paused/circuit_broken), `ScheduleSpec`,
`Occurrence`/`OccurrenceStatus`, `JobBudgets`, `RunOrigin`
(interactive/job), `ApprovalPolicy` (timeout/park), `ParkedApproval`,
`JobEvent` (SSE payload).

### vortex-core (`crates/vortex-core/src/`)

- `paths.rs` — `Paths::resolve()`: `VORTEX_*_DIR` (absolute, required) →
  `$HOME/<xdg-style default>`/vortex; creates all three dirs; derives
  `database()`, `config_file()`, `browser_profile()`, `trash_dir()`.
- `config.rs` — `AppConfig::load` precedence pipeline (§6); minimal `.env`
  parser (`load_dotenv`, never overwrites existing env); loopback
  enforcement: non-loopback `host` is a hard error unless LAN mode is
  enabled (`config.rs:131-144`); `ensure_private_config_perms` chmods
  config.toml to 0600.
- `db.rs` — single SQLite connection behind `Arc<Mutex<_>>`; pragmas
  `journal_mode=WAL`, `foreign_keys=ON`, `synchronous=NORMAL`; all queries go
  through `with_conn` → `tokio::task::spawn_blocking`; migration is
  `CREATE … IF NOT EXISTS` batch (no versioning);
  `mark_interrupted_on_startup` flips queued/running/waiting_approval runs to
  `interrupted` (nothing is replayed).
- `store*.rs` — conversations (`store.rs`), messages + settings blob
  (`store_msgs.rs`), runs with upsert/status updates (`store_runs.rs`), tool
  calls (`store_calls.rs`), approvals (`store_appr.rs`), checkpoints
  (`store_ckpts.rs` — file content *before* modification, `original = None`
  means "file did not exist"; cursor-paginated listing returning
  `CheckpointInfo` metadata, content only via `get_checkpoint`). All values
  bound via `rusqlite::params!` (no SQL injection surface).
- `store_jobs.rs` — routines/jobs/occurrences: `create_routine` lands draft v1
  atomically; `add_routine_version` appends an immutable version (status never
  changes; pinned jobs keep running what they pinned); `activate_routine` /
  job activation are the human-only transition path; `create_job` also creates
  the job's dedicated conversation (`Job: <name>`) in one transaction;
  `insert_occurrence` returns `Ok(None)` on the UNIQUE(job_id, scheduled_for)
  conflict (the double-fire guard); startup sweep
  `mark_occurrences_interrupted_on_startup` mirrors the runs sweep;
  `occurrence_had_expired_approval` drives the parked-expired catch-up branch.
- `job_seeds.rs` — `seed_draft_routines`: the three shipped starter templates
  (morning research digest / repository health check / workspace inbox triage),
  seeded once at startup **only into an empty routines table**, always as
  drafts at v1; never overwrites or activates.

### vortex-llm (`crates/vortex-llm/src/`)

- `llm.rs` — `LlmClient` trait: `complete(&CompletionRequest, mpsc::Sender<
  LlmEvent>) -> Result<CompletionResponse, LlmError>` (deltas streamed via
  the channel; the returned value carries the full turn), `models()`,
  `describe()`. `LlmEvent` has a single variant, `TextDelta(String)` — tool
  calls and usage arrive only in the final response.
- `openrouter.rs` — `POST {base_url}/chat/completions` with `stream: true`;
  headers `Authorization: Bearer …`, `HTTP-Referer: http://127.0.0.1`,
  `X-Title: Vortex-Ai-Chat`. Timeouts: connect 10 s, read/stall 120 s (no
  total cap — deliberate for long generations). Tool-call accumulation:
  fragments merged per `index` — `id`/`name` set when non-empty, `arguments`
  appended; slot growth capped at 64 entries, out-of-range indexes ignored
  (`openrouter.rs`, `KNOWN_ISSUES.md` P3 fixed). Retries: up to 2 extra
  attempts with 1 s/3 s backoff for `RateLimited`/`Timeout`/`Network` and
  *5xx* `Provider` errors only — 4xx are terminal (C13 fixed) — and only
  while nothing has been streamed to the consumer; a retryable failure after
  partial delivery surfaces as an error instead of duplicating output
  (C3 fixed). Status mapping: 401/403→`InvalidCredentials`,
  402→`InsufficientCredits`, 404→`ModelNotFound`, 429→`RateLimited`,
  422→`MalformedStream`, else `Provider`.
- `sse.rs` — spec-oriented SSE parser: buffers bytes until `\n`, handles
  CRLF, converts only complete lines (UTF-8-safe across chunk splits),
  accumulates `data:` lines per event and dispatches on the blank line
  (multi-line `data:` joined with `\n`, one leading space stripped);
  `finish()` flushes an unterminated trailing event at stream end.
  `event:`/`id:` fields are ignored. Oversized input (1 MiB line / 8 MiB
  event) is reported via `take_overflow()` and fails the stream as
  `MalformedStream` instead of being silently dropped (C24 fixed).
- `mock.rs` — `MockLlm` with scripted `MockTurn`s (`text`, `tool_call`,
  `failure`); streams word-by-word with a 5 ms default delay (configurable
  via `with_delay` for cancellation tests); used by the offline test suites
  (failure scripting: `KNOWN_ISSUES.md` C23, fixed).

### vortex-agents (`crates/vortex-agents/src/`)

- `engine.rs` — the run loop (§11). `allowed_for_mode(mode, settings,
  browser_ok, origin)` builds per-run tool allow-lists: Chat = meta only;
  Research = search + delegate; Coding = files + commands + previews +
  delegate; Browser = browser + fetch + delegate; Agent = the union of
  research/coding/browser plus the authoring tools (`save_routine`,
  `list_routines`, `propose_schedule`) **only when the origin is not a job**
  (each further gated by settings/profile/availability). `start_chat_run`
  keeps the last 40 history turns. Job admission: `start_job_run` (origin Job,
  `ParkUntilDecided`, job budgets applied to the settings snapshot, job system
  prompt + the job conversation's bounded history) and `spawn_continuation`
  (seeded transcript verbatim, model inherited from the prior run row,
  budgets/workspace from the durable job row); `classify_last_step` marks an
  unconfirmed consequential (or unknown-tool) step `NeedsReview`, everything
  else `Safe`. `spawn_subagent`: child cancel token,
  depth cap 3, recursive delegation opt-in, allow-list is the *intersection*
  of the parent's list and the request. Event forwarders are **drained, not
  aborted**, at completion (queued tool events/deltas are delivered and
  `RunFinished` is published strictly last; a 2 s timeout bounds the drain
  as a safety net), and cancel/deadline paths **abort the provider task**
  (`KNOWN_ISSUES.md` C7/N8, fixed).
- `registry.rs` — single enforcement point (`ToolRegistry::execute`):
  unregistered → refused; not in the run's allow-list → refused;
  `available()` check; typed schema validation (specs in `schema.rs`
  generate the JSON Schema given to the model; unknown keys filtered; string
  args capped at 200 KB); `Risk::Consequential` → approval gate before
  execution.
- `workspace.rs` — `WorkspaceRoots::resolve`: canonicalized root; absolute
  paths must be inside; `..` rejected lexically; each existing component
  canonicalized and re-checked against the root (symlink escape defense);
  components that fail canonicalization but are themselves symlinks
  (dangling/unresolvable) are rejected outright, while plain missing
  components remain allowed for creation (`KNOWN_ISSUES.md` C2, fixed).
- `file_state.rs` — per-path `tokio::Mutex` map + cross-run ownership:
  coordinator may always write; a sub-agent cannot modify a file owned by
  another run.
- `tools_write.rs` — `guarded_write`: lock → ownership check → DB checkpoint
  of previous content → create dirs → write → record ownership; `edit_file`
  exact-once replace with unified diff (`similar`); `delete_path`
  (Risk::Consequential) moves to `data/trash/` instead of unlinking.
  Restricted profile blocks all writes. Checkpoint recording distinguishes
  "file absent" (NULL original = didn't exist) from "present but not UTF-8"
  (no row + warning — a NULL would have meant *delete on restore*).
- `tools_command.rs` — argv arrays only (no shell), binary resolved from
  PATH; `FORBIDDEN` patterns (sudo/su, `rm -rf /`, disk writers, power
  management…) never run even if allowlisted/approved; `SENSITIVE` patterns
  (package managers, git push, systemctl…) force approval; non-allowlisted
  commands require approval; own process group, output capped at 200 KB,
  timeout default 60 s (clamp 1–600), SIGTERM→SIGKILL group kill on
  timeout/cancel/shutdown (orphan-freedom verified by pgrep tests).
- `approvals.rs` — `ApprovalManager`: persist → publish `ApprovalRequested`
  → await oneshot resolvable **only** by `decide()` (called from the HTTP
  API). Per-request `ApprovalPolicy`: interactive `TimeoutSecs` auto-denies
  after `max(5 s)` and records `Expired`; job `ParkUntilDecided` waits
  indefinitely (run status `waiting_approval` in hub + DB), resolves on a
  human decision, and expires promptly when the run is cancelled (shutdown).
  Single-owner rule: exactly one of `decide` / timeout / cancel owns the DB
  write, so a late decision can never overwrite an expired row or vice versa.
  Tools see only the `ApprovalGate` trait — sub-agent self-approval is
  structurally impossible.
- `clock.rs` — pure schedule math (no I/O): 5-field cron validation (the
  `cron` crate parses 6/7 fields with seconds first, so a validated 5-field
  expression is prefixed `"0 "`), injectable `Clock` trait (`SystemClock` in
  production, fakes in tests), `next_tick` (strictly-after), `missed_ticks`
  (ascending, capped at the most recent 512), overlap decisions. DST contract:
  nonexistent local times skip; ambiguous times run once at the earliest
  instant; all comparisons on absolute instants. See §9 for the cron caveats.
- `supervisor.rs` — the job lifecycle state machine (§11): tick loop (1 s)
  driven by the persisted `next_run_at`, occurrence admission (job gate,
  single-flight, daily cap), startup `catch_up` (interrupted-occurrence
  decision tree + missed-tick policy), budgets/breaker bookkeeping, steer-note
  consumption, park forwarding, and a seq-stamped job-event log (1024 entries,
  hub-pattern replay/gap semantics). Started exactly once in `main.rs`.
- `tools_routines.rs` — `save_routine` (draft v1 only), `list_routines`
  (read-only), `propose_schedule` (draft job pinned to the routine's current
  version). All `Risk::Low`; no parameter list declares status/activation
  fields and `ToolDef::filter` strips unknown keys, so injected arguments
  cannot smuggle an activation. Interactive Agent runs only — stripped from
  job-origin runs at admission.
- `scheduler.rs` — global sub-agent gate: counter + `Notify` (50 ms poll
  fallback); `SlotGuard` releases on drop (cancellation- and panic-safe);
  limit default 6, min 1, ceiling 16, runtime-adjustable; the coordinator
  never consumes a slot; nested sub-agents share the same gate.
- `hub.rs` — run registry + event fan-out: per-run `broadcast::channel(512)`
  carrying `(seq, RunEvent)` plus a bounded in-memory replay log
  (`MAX_RUN_LOG = 8192` entries, oldest evicted). Seq allocation, log insert
  and broadcast send happen under one lock, so log order and stream order
  always agree; each handle (including ancestors) has its own seq
  namespace. `replay_from(run_id, since)` feeds SSE reconnects (§9). Events
  published to the run **and all ancestors** (one SSE subscription covers a
  whole agent tree); `cancel`/`cancel_all` via `CancellationToken`s. The
  log dies with the run handle — runs never survive restarts, so nothing is
  persisted.
- `preview.rs` / `preview_server.rs` / `tools_preview.rs` — static previews:
  small loopback-only Rust HTTP server (GET/HEAD, 16 KiB header cap, `..`
  rejected, canonicalized root-prefix guard, ephemeral port). Dev-server
   previews: approval required, spawned in own process group; port detection
   (≤ 20 s) matches stdout against a URL/port regex but **only accepts a
   port that shows up as a new LISTEN socket** in `/proc/net/tcp{,6}`
   compared against a pre-spawn snapshot (listener-ownership check,
   `KNOWN_ISSUES.md` P9 fixed); fallback: exactly one new listener and no
   parseable output; 8417 always excluded. Killed on run end/cancel/
   shutdown (the registry owns the `Child` handle; see `KNOWN_ISSUES.md`
   C1, fixed).
- `browser.rs` / `cdp.rs` / `tools_browser.rs` — Chromium detection in PATH
  (`VORTEX_CHROME_PATH` overrides); launched headless with isolated
  `--user-data-dir` under the XDG cache, own process group,
  `--remote-debugging-port=0`; DevTools ws URL read from stderr (15 s,
  loopback-only URLs accepted); minimal CDP client over websocket
  (Target.createTarget/attachToTarget, Page.navigate, Runtime.evaluate;
  per-command timeouts 10–30 s); one page per run, closed at run end.
   Navigate/read restricted to http/https (`file://`, `chrome://` refused);
   typing into password fields refused; login/CAPTCHA presence reported for
   human handoff (the manager owns the `Child` handle; see
   `KNOWN_ISSUES.md` C1, fixed).
- `safe_http.rs` / `html.rs` — SSRF guard for model-chosen URLs: http/https
  only; DNS resolved once per hop and **every** address checked against
  loopback/RFC1918/link-local/broadcast/ULA/IPv4-mapped-IPv6 before
  connecting; the connection is then **IP-pinned** to a validated address
  via a per-hop reqwest client with `.resolve(host, addr)` (TLS SNI and
  certificate verification still use the hostname), closing the DNS
  rebinding TOCTOU window (`KNOWN_ISSUES.md` P1, fixed); redirects disabled
  in reqwest and re-validated + re-pinned per hop (max 5); content-type
  allowlist; streamed body cap. Cost: one client build per hop — acceptable
  at tool-call frequency. Constructed with `allow_private_hosts = false` for
  all model-chosen URLs (`vortex-server/src/main.rs`); only the
  user-configured search provider may be local (shared unpinned client).
- `search.rs` / `tools_search.rs` — `SearxngProvider` (user-configured base
  URL, JSON format) and `MockSearchProvider`; `web_search` (result count
  from settings) and `fetch_url` (SafeHttp, 2 MB body cap, text truncated to
  12 000 chars, HTML stripped).
- `tools_delegate.rs` / `tools_meta.rs` / `prompts.rs` — `delegate_subtask`
  (gated by delegation setting + depth/recursive rules), `update_plan`,
  `request_approval` (model-initiated pause for consequential web/external
  actions). System prompts mark tool/web content as untrusted and state the
  no-self-approval rule — but *enforcement is entirely server-side*; prompts
  are guidance only.

### vortex-server (`crates/vortex-server/src/`)

- `main.rs` — startup order: paths → config → logging (policy: never log
  request headers/bodies) → DB + interrupted-run marking (+ expiry of their
  pending approvals) → interrupted-occurrence sweep → draft routine template
  seeding (log-only on failure) → settings → LLM provider selection (mock vs
  OpenRouter; starts without a key but warns) →
  hub/scheduler/browser/previews/search/approvals → engine → supervisor
  created and `run()` spawned **exactly once** (catch-up, then 1 s ticks) →
  LAN token handling → router → graceful shutdown (cancel the supervisor
  FIRST so no orphan ticks admit new work, then cancel all runs, stop all
  previews, close browser).
- `routes_jobs.rs` — routines/jobs/occurrences REST + the jobs SSE channel +
  the parked-approval inbox (§9). Activation is a distinct human endpoint;
  manual runs insert a `scheduled` occurrence that the supervisor's due-query
  admits; `resolve-review` continues or dismisses a flagged occurrence.
- `guard.rs` — middleware on every route: Host allow-list
  (`127.0.0.1`/`localhost`/`::1`) unless LAN mode (DNS-rebinding defense);
  Origin check on non-GET/HEAD/OPTIONS writes (loopback origins only;
  skipped in LAN mode where the token is the gate); LAN mode requires
  `Authorization: Bearer <token>` or `?token=` (for EventSource, which
  cannot set headers). 2 MiB body limit.
- `routes_conv.rs` / `routes_runs.rs` / `routes_misc.rs` /
  `routes_ckpts.rs` — REST surface (§9). Notable: `post_chat` pre-flight
  refuses with 503 when no key and no mock; SSE `run_events` replays the
  run's retained event log from the client's cursor (`Last-Event-ID` header
  or `?since=`), stamps every event with `id: <seq>`, dedupes the
  replay/live overlap per connection, and emits a `replay_gap` event when
  the cursor predates the retained window (or the consumer lagged);
  terminal/unknown runs still get a single synthesized `run_finished` so
  late subscribers settle. `routes_ckpts.rs` serves checkpoint listing and
  the human-initiated restore flow (reversible: the current content is
  snapshotted first; confined to the current workspace).
- `static_files.rs` — rust-embed serving of `ui-dist/` (disk in debug,
  embedded in release); blocks `..`/leading-`/` paths; SPA fallback for
  dot-less paths; instructional placeholder when `index.html` is missing.
- `mock_llm.rs` — `DemoMockLlm` for `VORTEX_LLM=mock` (§5).

### vortex-ui (`crates/vortex-ui/src/`)

Leptos 0.8 CSR app; global state is an `AppCtx` of 18 `RwSignal`s
(`state.rs`). `lib.rs` boots (settings → health → conversations →

Recovery: every SSE event carries the server's per-run sequence as its

are filtered to the subscribed run, so sub-agent streams and statuses never
leak into the coordinator's UI; an orphan `ToolCallFinished` is inserted as
a recovered row. Terminal `RunFinished` triggers a full message refetch
(the final reconciliation point). `chat.rs` renders the message list,
optimistic user bubble (unique negative ids), the streaming bubble (reads
the throttled `stream_display` mirror of `stream_text`, so markdown +
syntax highlighting re-render ≤8×/s instead of per delta), Stop/Retry
controls.
`sidebar.rs` conversation list/search/rename/delete + workspace picker
(server-validated). `tasks.rs` approvals/plan/tool-calls/sub-agents/
previews/file-checkpoints panels (the checkpoint panel lists snapshots for
the current conversation with cursor pagination and a confirm-guarded
Restore button). `settings_ui.rs` draft-pattern settings form.
`markdown.rs` hand-rolled pulldown-cmark walker: raw HTML is never emitted,
all text escaped, links restricted to `http(s)`/`#` (everything else becomes

### SSE

`GET /api/runs/{id}/events` — text/event-stream of the run **and its whole
sub-agent tree** (child events are fanned up to ancestor channels; each
channel has its own sequence namespace). 15 s keep-alive pings.

Every event carries `id: <seq>` — the hub's per-run monotonic sequence. On
(re-)subscription the server replays its retained run log (8192 entries)
from the client's cursor, then tails the live broadcast with per-connection
deduplication:

- Cursor sources: the `Last-Event-ID` request header (sent automatically by
  the browser's `EventSource` on reconnect) and/or `?since=<seq>` (used by
  the UI for manual re-subscribes). When both are present, the larger wins;
  with neither, the full retained log is replayed from seq 1.
- If the cursor predates the retained window (events were evicted), a named
  `replay_gap` event is emitted first (data = oldest retained seq) and the
  client is expected to resync from `GET /api/runs/{id}/state`. Broadcast
  buffer overflow (`lagged`) maps to the same `replay_gap` event.
- A cursor *above* the newest seq (a future/stale value) is clamped, not
  honored literally: no gap is signaled and the live tail keeps flowing.

Terminal/unknown runs replay a single synthesized `run_finished` event with
the stored status (so late subscribers settle); no ids are stamped there.

Event catalog (`RunEvent`, serde `tag = "type"`, snake_case;
`vortex-types/src/events.rs:71-139`):

| `type` | Fields | Meaning |
| --- | --- | --- |
| `run_started` | run_id, parent_run_id?, agent, model, task, depth | run (or sub-agent) began |
| `text_delta` | run_id, delta | streamed assistant text chunk |
| `plan_updated` | run_id, steps[{title,status}] | model updated its plan |
| `tool_call_started` | run_id, call_id, tool, args | tool execution began |
| `tool_call_finished` | run_id, call_id, ok, summary, diff? | tool result (diff = unified diff for file writes) |
| `approval_requested` | approval_id, run_id, agent, title, payload | awaiting human decision |
| `approval_resolved` | approval_id, run_id, approved | decided or expired |
| `usage_update` | run_id, usage{prompt,completion,total} | cumulative token usage |
| `preview_started` | run_id, preview_id, url | preview server launched |
| `status_changed` | run_id, status, detail? | run status transition |
| `run_finished` | run_id, status, error? | terminal |

### Jobs & routines API

Durable autonomous work: versioned **routines** (instruction templates),
**jobs** (a pinned routine version + schedule + guardrails), and
**occurrences** (one execution of a job). Handlers live in
`crates/vortex-server/src/routes_jobs.rs`; the lifecycle state machine is
`vortex-agents/src/supervisor.rs` (started exactly once in `main.rs`, tick
loop every 1 s, job gate of 2 concurrent job roots independent of the
sub-agent scheduler). All routes sit inside the same guard layer; errors are
uniform `{"error": "…"}` with actionable 400s.

**Safety model (server-enforced, never by prompt):** routines created via
`POST /api/routines` (including agent-drafted ones) always land as `draft`;
only the human activate endpoints flip status. Jobs pin an exact routine
version — editing a routine never changes what a pinned job runs. Job-origin
runs never receive routine/job-authoring tools, and their consequential
actions park until a human decides (no auto-deny timeout).

| Method & path | Purpose |
| --- | --- |
| `GET /api/routines` | `Routine[]` (most recently updated first) |
| `POST /api/routines` | `{name, instructions, description?, mode?, model?}` → `Routine` (always draft, v1 written atomically; `mode` defaults to `"agent"`, validated by serde) |
| `GET /api/routines/{id}` | `{routine, versions}` (versions newest first); 404 when missing |

| `POST /api/routines/{id}/archive` | draft\|active → archived; 409 when already archived |
| `POST /api/routines/{id}/versions` | `{instructions, mode?, model?}` → `RoutineVersion` (bumps `current_version`; status unchanged) |
| `GET /api/jobs` | `Job[]` (oldest first) |

Both clear the review flag |

Schedules are standard **5-field cron** (minute hour day-of-month month
day-of-week), validated by `vortex-agents/src/clock.rs`; v1 timezones are
server-local only (`tz: "local"` or empty — anything else is a 400).
`missed_policy` is `run_once_if_missed` (default: one catch-up occurrence for
the most recent missed tick) or `skip`; `overlap` is `skip` (default) or
`queue_one`. Budget defaults: 12 turns, 120 000 tokens, 24 occurrences/day,
600 s per occurrence; the breaker pauses a job after 3 consecutive
failed/parked-expired occurrences (human resume resets the counter).

**Cron caveats (read before writing schedules):**

- 6/7-field expressions (seconds/years) are rejected — the `cron` crate
  parses those natively, so Vortex validates the 5-field shape first and
  prefixes `"0 "` internally.
- When **both** day-of-month and day-of-week are restricted, the `cron` crate
  **ANDs** them (vixie cron ORs). `0 9 13 * FRI` fires only on Friday the
  13th, not on every 13th AND every Friday.
- The crate's year range is **1970–2100**; past 2100 `next_tick` returns
  `Ok(None)` (the expression can never fire again) and `next_run_at` clears.
- Missed-tick enumeration is capped at the **most recent 512** ticks, so a
  long downtime cannot produce an unbounded catch-up list (and the policy
  fires at most one occurrence anyway).
- DST: nonexistent local times (spring forward) are skipped; ambiguous times
  (fall back) fire exactly once, at the earliest instant.
- Firing is driven by the persisted `next_run_at` (the previously computed
  next fire time): `next_tick` is strictly-after, so a brand-new active job
  seeds `next_run_at` on its first observed tick and fires from the next one.
  A clock jump backward never re-fires an already-fired tick — the
  UNIQUE(job_id, scheduled_for) constraint is the double-fire guard.

**Seed templates.** On first startup (empty routines table only) the server
seeds three DRAFT templates — *Morning research digest* (Research),
*Repository health check* (Coding), *Workspace inbox triage* (Agent) — via
`vortex-core/src/job_seeds.rs`. They never run until a human activates them
and pins them to a job; an existing routine library is never touched.

**Jobs SSE channel.** `GET /api/jobs/events` mirrors the run-event stream
exactly (one channel for all jobs, no run-id path): seq-stamped `id:` fields,
`Last-Event-ID` header and/or `?since=<seq>` cursor (larger wins), replay of
the retained log (1024 entries) before the live tail with per-connection
dedup, a named `replay_gap` event when the cursor predates the retained
window (data = oldest retained seq; resync from `GET /api/jobs`), future
cursors clamped, 15 s keep-alive pings. Event catalog (`JobEvent`, serde
`tag = "type"`, snake_case): `job_updated`, `routine_updated`,
`occurrence_updated`, `approval_parked`, `job_circuit_broken`. Events are
emitted by the **supervisor** (occurrence transitions, `next_run_at`
maintenance, breaker trips, parked approvals); REST mutations do not publish
to the channel — clients refetch after mutations. (`routine_updated` is
declared in the DTO but never emitted by the supervisor today; routine
changes are visible via refetch.)

**Honest limitations.** Jobs fire only while Vortex is running (in-process
tokio loop; no OS timers). At startup, live occurrences are marked
`interrupted` (mirroring the runs sweep) and the supervisor's catch-up
decides continuation per policy: safe step boundaries continue from the
persisted transcript + plan; an unconfirmed consequential step is flagged
`needs_human_review` and never auto-re-executed; parked approvals that
expired on restart count toward the breaker. Nothing consequential is ever
replayed automatically.

## 11. Agent loop semantics

Per run (`engine.rs`, see §7):

- **Iterations**: `for _ in 0..max_iterations` (default 16, clamp 1–64).
  Exhaustion → run `failed` with "iteration limit reached".
- **Wall clock**: deadline = start + `run_timeout_secs` (default 600 s,
  floor 30 s), enforced via `tokio::select!` around the LLM call.
- **Tokens**: enforced *before every provider call* — the run fails when
  `max_total_tokens` (default 200 000) is exhausted, and each request's
  `max_tokens` is clamped to the remaining budget, bounding any overshoot
  to one clamped completion; a post-tool check remains as a backstop
  (`KNOWN_ISSUES.md` P15, fixed).
- **History**: coordinator runs replay the last 40 stored turns; tool
  results are appended as `tool` messages within the run.
- **Cancellation**: `CancellationToken` tree — sub-agents get
  `parent.child_token()`, so stopping a coordinator stops all descendants;
  `POST /api/runs/{id}/stop` cancels one tree; server shutdown cancels all.
  Cancelling (or hitting the deadline) **aborts the in-flight provider
  task**, so the completion stream stops being consumed immediately
  (`KNOWN_ISSUES.md` N8, fixed).
- **Tool execution**: calls within one assistant turn run concurrently as
  spawned tasks; a panicking tool becomes a failed tool result, not a run
  crash; every call is persisted (`tool_calls` running → completed).
- **Approvals**: `Risk::Consequential` (`delete_path`) plus in-tool gates
  (`run_command` sensitive/non-allowlisted, dev-server previews, explicit
  `request_approval`) pause the run (`waiting_approval`) until a human
  decides via the API or the timeout (default 300 s, floor 5 s) auto-denies.
- **Sub-agents**: `delegate_subtask` → scheduler slot (global semaphore,
  default 6, ceiling 16; coordinator exempt; nested agents share the gate) →
  depth ≤ 3, recursion beyond depth 1 only if `agents.recursive` → child
  allow-list = intersection(parent allow-list, requested tools) — a
  sub-agent can never widen its permissions; its events fan up to ancestor
  SSE channels; on run end: previews stopped, browser page closed, file
  ownership released.
- **Completion**: with no tool calls, the assistant message is the final
  answer and (for root runs) is persisted to the conversation. Partial text
  from failed/cancelled runs is *not* persisted as a message.

### Jobs: architecture & occurrence lifecycle

The autonomous path layers on the same run machinery — nothing is re-executed
mid-loop, and every capability decision stays server-side:

```
store_jobs.rs (durable SQLite: routines/jobs/occurrences)
   ▲                                    │
   │ transitions                        │ due queries / job rows
clock.rs (pure cron math,               ▼
 injectable Clock)  ──▶  supervisor.rs (tick loop, 1 s; started ONCE)
                           │  admission: job gate → single-flight → daily cap
                           ▼
                         engine.rs (start_job_run / spawn_continuation)
                           │  origin=Job, ParkUntilDecided, job budgets,
                           │  authoring tools stripped, job workspace pinned
                           ▼
                         run loop (§11) → hub events → supervisor forwards
                           │  parks/breaker/outcomes back to the store
                           ▼
                         routes_jobs.rs (REST + SSE) → Jobs tab (WASM UI)
```

- **Occurrence lifecycle**: `scheduled` (inserted for a tick — live fire,
  catch-up, or manual run) → `running` (engine admitted a run) →
  (`waiting_approval` ⇄ `running`)* → `succeeded` | `failed` | `skipped`.
  A process death leaves `running`/`waiting_approval` rows; the startup sweep
  marks them `interrupted` (mirroring the runs sweep) and the supervisor's
  catch-up decides what happens next. `skipped` covers overlap collisions,
  the daily cap, and non-active jobs; skipped rows never count toward the
  daily cap.
- **Continuation decision tree** (catch-up, per unprocessed `interrupted`
  occurrence with a run attached):
  1. job not active → deferred (`interrupted`, reason recorded);
  2. the run had an approval that **expired on restart** → parked-expired:
     counts toward the breaker, never continued (a human must re-decide);
  3. `classify_last_step` on the persisted tool-call history: an unconfirmed
     (`summary = "running"`) consequential step — or an unconfirmed call to a
     tool the registry no longer knows — → `NeedsReview`: the occurrence is
     flagged `needs_human_review` and a human resolves it via
     `POST /api/occurrences/{id}/resolve-review` (`continue` re-admits through
     this same tree; `dismiss` fails it without touching the breaker);
  4. otherwise `Safe` → a **continuation run** is spawned, seeded from the
     persisted transcript (bounded 40-message window) + prior plan + a
     continuation instruction that forbids redoing completed steps. The
     continuation inherits the prior run's resolved model and the job's
     durable budgets/workspace. Nothing is replayed mid-loop.
- **Job gate vs sub-agent cap**: job roots consume a dedicated counting
  semaphore (default **2**, clamped 1–16) — independent of the sub-agent
  scheduler, so jobs never starve interactive use and vice versa. Job roots
  do NOT consume sub-agent slots; nested delegates from a job run still share
  the global sub-agent cap (default 6). Continuations consume a job-gate slot.
- **Single-flight & overlap**: an occurrence never overlaps itself. With
  `overlap: skip` (default) a colliding tick is skipped; with `queue_one` one
  colliding occurrence stays `scheduled` and is admitted when the live one
  drains (a third collision skips).
- **Budgets & breaker**: per-occurrence turn/token/wall-clock caps reuse the
  engine budget plumbing (`max_iterations`, `max_total_tokens`,
  `run_timeout_secs` with a 30 s floor); the per-job daily cap counts today's
  non-skipped occurrences (local midnight window). 3 consecutive
  failed/parked-expired occurrences trip `circuit_broken`; user cancellation
  and human dismissal never count; a successful occurrence or a human resume
  resets the counter.
- **Steer notes**: `POST /api/jobs/{id}/steer` persists a one-shot note that
  the supervisor appends to the pinned instructions of the **next**
  occurrence or continuation, then clears it (consumed once). Mid-run message
  injection into a live loop is out of scope in v1 — cancel, approval
  decisions, and steer notes are the control surface.
- **Restart honesty**: live runs are marked `interrupted` and their pending
  approvals expired at startup; live occurrences likewise. Catch-up never
  re-executes an unconfirmed consequential step. The failure-injection matrix
  proving all of the above lives in
  `crates/vortex-server/src/job_hardening_tests.rs` (offline: tempdir DB,
  scripted LLM, fake clock, manual ticks).

## 13. Edge cases & known limitations

Consolidated (full details with evidence in [`KNOWN_ISSUES.md`](KNOWN_ISSUES.md)
and [`SECURITY.md`](SECURITY.md)):

- **A real OpenRouter API key is required** for any real use; without one
  the server starts but chat returns 503. The mock provider is a plumbing
  test harness only.
- Browser tools and dev-server previews were broken at runtime (spawned
  processes were killed immediately after launch — `KNOWN_ISSUES.md` C1,
  **fixed** with regression tests; live browser verification still requires
  a machine with Chromium installed).
- Live OpenRouter streaming has only been verified against a
  protocol-faithful local mock; real-provider framing differences are
  possible (P14 — an opt-in `#[ignore]`d live smoke test now exists, see
  §12; it has deliberately not been run yet because it costs credits).
- Mid-stream retries no longer duplicate streamed text (C3, fixed: retries
  stop once anything was delivered); the server keeps a per-run event log
  (8192 entries) and the SSE route replays it from the client's cursor, so
  reconnects recover missed events (C7, fixed). Residual: if the retained
  window overflows (extreme event bursts), the client gets `replay_gap` and
  resyncs from the snapshot — text deltas lost that way are not
  reconstructible mid-run (the snapshot has no accumulated assistant text);
  the bubble heals at run end via the terminal message refetch.
- Dangling symlinks inside the workspace are rejected on resolve (C2,
  fixed); model-chosen fetches are IP-pinned after validation, closing the
  DNS-rebinding TOCTOU window (P1, fixed).
- The workspace is **not** a sandbox: commands run with your user rights;
  there is no container/namespace isolation (by design, stated plainly in
  `SECURITY.md`). Job workspaces (including the per-job scratch dirs) get the
  same confinement — and the same limitation.
- Jobs fire **only while Vortex is running** (in-process loop, no OS timers);
  schedules use the server's local timezone only in v1; mid-run steering is
  out of scope (steer note + cancel + approvals cover control). See §9 cron
  caveats (dom+dow AND semantics, 1970–2100 year range, 512 missed-tick cap).
- LAN mode: token-gated but no TLS; the WASM UI cannot send the token, so
  LAN mode is API-only in practice.
- CI workflow (`.github/workflows/ci.yml`) and `LICENSE` (MIT) now exist,
  but CI has not been exercised on GitHub Actions yet and the `main` branch
  is still stale (C22 residual — pushing is a user action).
- Wayland/X11 desktop automation is not implemented; no packaging
  (.deb/.rpm) or install wizard — run the binary as your own user (no root,
  no services).
